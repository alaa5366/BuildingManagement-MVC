The checked-in target entity inventory explicitly classifies most legacy tables as **Retain legacy initially** and states that legacy retirement is a separate operation after an accepted module cutover. The current repository still contains legacy EF mappings and active legacy application dependencies.

Therefore:
- No `DROP TABLE`, `TRUNCATE`, `DELETE`, or FK disabling is performed or generated by Phase 52.
- No table is considered droppable merely because a canonical target table exists or a backfill report says reconciliation passed.
- `Buildings`, `Floors`, and `Apartments` are permanent shared property foundations for this redesign and are explicitly retained.
- Finance source tables remain authoritative until finance cutover and exact parity acceptance.
- `__EFMigrationsHistory` is infrastructure metadata and must not be dropped while EF Core uses it.
- The only database allowed for any future retirement script is the exact disposable target `BuildingManagement_RestoreTest`.

## 3. Backfill evidence is not cutover evidence

The mapping document reports successful additive reconciliation for several phases, including Notifications, MaintenanceRecords, AuditLog and BackupHistory; it also records later operational migration work for Presence, QR, Polls, media, permissions and other domains. These are evidence-preservation/backfill steps only. The same document explicitly says legacy tables remain unchanged and authoritative until application read/write transition is separately implemented and verified.

A target table or migration map can be an archive/evidence destination without being a complete operational replacement. In particular:
- Poll vote evidence is not a replacement voting workflow.
- DVR/camera metadata evidence is not a functioning credential-safe media module.
- UserPermissions evidence is not equivalent to effective target authorization.
- Backup job metadata is not equivalent to a verified backup artifact and tested restore path.
- Presence snapshot migration is not equivalent to live per-account/device session tracking.

## 4. Preconditions for the one-batch retirement operation

A future retirement batch may be generated only after **all** following checks pass for every table in its explicit allowlist:

1. Target database identity is verified as exactly `BuildingManagement_RestoreTest` immediately before execution.
2. Source database `BuildingManagement` is never opened for write and is never named as a DDL/DML target.
3. Full schema/column/key/FK comparison is complete; source row counts and stable fingerprints are reconciled to durable target records or an immutable archive.
4. Every source row has a durable source key, source table identity, provenance/fingerprint and an explicit disposition; unresolved rows block retirement.
5. All target FK relationships and cross-building integrity checks pass.
6. All EF mappings, SQL, stored procedures, views, background jobs, scripts, controllers, services, views and integrations no longer require the retiring object.
7. The owning module's read/write cutover, authorization tests, data parity tests, performance checks and rollback rehearsal are accepted.
8. Runtime queues and in-flight work are drained or migrated; no pending sync changes are discarded.
9. A restore point/backup of the disposable target is verified and the rollback procedure is rehearsed.
10. One reviewed explicit allowlist is used. No wildcard discovery-driven DROP and no automatic dropping based on same-name target existence.
11. The entire eligible set is executed as one controlled batch/transaction where SQL Server object dependencies permit; any precondition failure aborts the whole operation.
12. `Buildings`, `Floors`, `Apartments`, `__EFMigrationsHistory`, and any table without a completed domain cutover are excluded.

## 5. Sequencing decision

The requested two-step sequence is preserved, with a safety prerequisite made explicit:

- **Stage 1 — one-batch legacy retirement:** run only after target data/provenance acceptance and the necessary cutover compatibility is already in place. All eligible obsolete tables are removed in one reviewed batch; retained foundational/domain tables stay.
- **Stage 2 — MVC refactoring and log-center UX:** update controllers, services and views to use the canonical target models only; rebuild the log screens around bounded search, severity, time range, correlation, details, paging and Audit Trail integration.

Because the current refactoring map and target inventory still show active legacy dependencies and multiple target entities are only logical candidates, Stage 1 currently has an empty authorized DROP allowlist. This is a deliberate safety result, not a skipped deletion.

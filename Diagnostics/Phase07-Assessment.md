# Phase07 – Application Data Integrity & Concurrency Assessment

**Status:** In progress – diagnostics only  
**Branch:** `development/phase07-application-data-integrity`  
**Baseline:** Accepted Phase05 schema/index cleanup and Phase06 read-only index assessment  
**Database scope:** TEST only (`BuildingManagement_RestoreTest`)  
**Production:** Explicitly excluded

## Objective

Assess application-level data invariants that are not fully represented by primary/foreign keys, and identify concurrency-sensitive write paths before proposing any schema or code change.

Phase07 begins as a read-only assessment. No migration, data repair, constraint addition, or production operation is authorized by this document.

## Evidence-based areas selected for review

The current schema and application code show several business rules enforced primarily in application code rather than SQL constraints:

- Expense and revenue amounts are normalized/validated in `BuildingSqlMapper.SaveAsync`.
- Deposit amount and status are validated in the aggregate mapper.
- Month keys are validated in the aggregate mapper using a strict `yyyy-MM` rule.
- Apartment primary-resident selection is represented by `Residents.IsPrimary`; the current schema does not declare a filtered unique constraint for one primary resident per apartment.
- Deposit display numbers are generated by scanning existing numbers in a building/month; the database primary key is based on `BuildingId + Id`, not the display number.
- Building/global/backup settings contain numeric policy fields whose allowed ranges need confirmation against product rules.

These are investigation targets, not yet confirmed defects. In particular, multiple primary residents may be legitimate under an undocumented business rule, and no existing data should be changed based only on a diagnostic result.

## Deliverable in this stage

`Diagnostics/Phase07_DataIntegrityDiagnostics.sql` is a read-only SQL Server 2017+ script. It reports:

1. Database/server capture information.
2. Negative/non-positive amounts and unknown domain values.
3. Malformed month keys across financial and wallet tables.
4. Expense/revenue transaction dates that differ from their month key (review only).
5. Apartments with multiple primary residents (review only).
6. Duplicate deposit display numbers within a building/month.
7. Settings values outside preliminary numeric bounds (review only).
8. Disabled or untrusted foreign-key/check constraints.
9. Existing CHECK-constraint inventory.

The script contains no DML or DDL. Result sets are diagnostic signals; they do not authorize automatic cleanup.

## Acceptance gates

Before implementation is considered:

1. Run the script against `BuildingManagement_RestoreTest` only.
2. Review every non-empty result set and distinguish real violations from permitted business behavior.
3. Confirm the intended business rule for primary residents and deposit numbering with the application behavior.
4. Identify the exact write paths and tests for each confirmed issue.
5. Propose only the smallest safe code/schema change, including a preflight query and reversible migration if a constraint is justified.
6. Preserve all existing data. No destructive cleanup based only on this assessment.
7. Run `dotnet build` and the complete test suite locally after any code change.

## Explicit non-goals

- No index additions/removals (Phase06 decision remains accepted).
- No table/column deletion.
- No data cleanup or normalization.
- No production database access or migration.
- No assumption that every diagnostic result is an error.

## Current outcome

Phase07 is opened as a controlled data-integrity assessment. Implementation decisions remain pending TEST evidence and business-rule confirmation.

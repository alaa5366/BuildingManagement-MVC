## Findings and remediation

### SF10-01 — Resident administration did not enforce `residents.manage`

**Severity:** High  
**Evidence:** `AdminResidentsController` had role and building-scope checks, but no `AdminPermission` filter. The separate `residents.manage` permission was already defined and applied to `AdminAptsController`, leaving the resident CRUD endpoints accessible to any admin in the building regardless of that permission.

**Remediation:** Added `[AdminPermission(AdminPermissions.ManageResidents)]` to `AdminResidentsController`. Super-admin behavior and existing building scoping remain unchanged.

### SF10-02 — Building settings did not enforce `settings.manage.building`

**Severity:** High  
**Evidence:** Both GET and POST `SettingsController.Building` actions enforced role and building scope but omitted the existing building-settings permission.

**Remediation:** Applied `[AdminPermission(AdminPermissions.ManageSettingsBuilding)]` to both actions. Super-admin bypass remains consistent with the existing permission filter.

### SF10-03 — Camera viewing did not enforce `cameras.view`

**Severity:** High  
**Evidence:** `CamerasController.Live` and `GetHlsUrl` enforced authentication and building scope but did not enforce the existing `cameras.view` permission for admins.

**Remediation:** Applied `[AdminPermission(AdminPermissions.ViewCameras)]` at controller level. The existing filter requires the permission for admins while retaining resident access and super-admin bypass.

### SF10-04 — Audit-log permission catalog was not enforced by its endpoints

**Severity:** High  
**Evidence:** `ViewAuditLogBuilding` and `ViewAuditLogOwn` existed in the permission catalog and role templates, but the controller only checked role and scope.

**Remediation:** Both `Index` and `ExportCsv` now require the matching role-scoped permission:
- Super-admin: unrestricted.
- Admin: `audit.view.building`.
- Resident: `audit.view.own`.

Existing building/apartment scope restrictions remain in place. Added a testable access policy and role/permission matrix tests.

### SF10-05 — Resident diagnostic action exposed authentication claims

**Severity:** Medium  
**Evidence:** `ResidentHomeController.Debug` returned every claim to any authenticated resident.

**Remediation:** Removed the diagnostic action. The production resident dashboard is unchanged.

### SF10-06 — Duplicate HTTP method metadata on two actions

**Severity:** Medium  
**Evidence:** Duplicate `[HttpPost]` on `QrAccessController.Confirm` and duplicate `[HttpGet]` on `ResidentPollsController.Index`.

**Remediation:** Removed duplicate attributes and added a reflection regression test that rejects repeated HTTP method metadata on controller actions.

### SF10-07 — Unexpected exception details were returned to users

**Severity:** Medium  
**Evidence:** Several administrative, settings, backup/import, wallet-update, and resident receipt-OCR paths appended raw exception messages to TempData or JSON responses.

**Remediation:** Replaced unexpected exception details with stable localized errors. Backup and settings paths retain structured server-side exception logging. The wallet's explicit `InvalidOperationException` business-validation response is retained because it is generated by the wallet domain service for known validation conditions; unexpected exceptions are generic.

## Additional review conclusions

- Sensitive state-changing MVC actions reviewed use POST and antiforgery validation. The intentional exceptions are capability-token-based anonymous QR/quick-login/PIN flows and the authenticated self-heartbeat endpoint; these were not changed in this phase.
- Existing resident/admin building and apartment scoping was retained; the permission fixes do not widen data scope.
- Financial service checks already enforce positive deposit amounts and pending-only deposit confirmation/edit/cancellation. Existing wallet transaction, carry-over, and concurrency tests remain part of the regression suite.
- Existing backup/restore hardening from the earlier implementation branch was not duplicated or rewritten.
- No verified need for a database schema/data change was found in this phase.
